## Booking trust and durability

`api/_shsat-questionnaire.js` validates all six answer fields, parent role, grade5–9, contact and offered calendar slot on the final POST. It ignores client completion/eligibility flags and derives the band itself. Complete means a structurally complete set of self-reported answers; it does not authenticate a person's age/parenthood or attest that a human clicked every UI step.

Before Calendar is called, `api/_shsat-store.js` reserves phone/IP capacity across instances in a Postgres transaction using a shared transaction advisory lock. The limits are two booking intake attempts per phone/day and five per IP/hour; pending and failed attempts count. The selected slot is also reserved with a unique constraint, preventing two eligible requests from booking it concurrently through this path. Existing outside-calendar events still use the calendar free/busy check. Unknown IP or store failure blocks the write. The server accepts only a single syntactically valid `x-vercel-forwarded-for` in a deployment with server-owned `VERCEL=1` and `VERCEL_ENV=production|preview`. Arrays, chains, malformed values, zone identifiers, direct sockets, `x-real-ip` and generic `x-forwarded-for` never supply a fallback identity. IPv6 is canonicalized, including IPv4-mapped addresses. Local fixtures inject their own explicit server resolver. Verify actual proxy behavior before release. Vercel documents the platform-owned header separately from a potentially overwritten proxy header: https://vercel.com/docs/headers/request-headers

The intake snapshot is encrypted with AES-GCM; contact lookup keys/fingerprints use purpose-separated HMACs. No key is embedded. Server creates an opaque receipt internally from the exact normalized intake. The client does not supply a trusted eligibility boolean or choose the summary. A changed answer/contact with the same quiz ID conflicts. The booking reservation binds the exact slot and deterministic Google event/conference ID. The server-owned canonical labels appear in the owner's primary-calendar description, labeled as the parent's own answers, not a score. The existing business calendar identity must be verified in the release gate.

An exact accepted booking is looked up by the normalized intake fingerprint and bound slot before current lead-time rules; this is read-only and remains replayable after capability expiry. New writes still require a live receipt and current offered slot. Every fresh provider check consumes a durable reservation, including known pre-insert slot rejections, with at most five checks per phone/day and IP/hour and at most five per attempt/identity. The existing insert-only reservation table and advisory transaction enforce the bound across instances; terminal accepted/unknown replays never call the provider again. No new schema or grants are needed for this correction.

Trusted SHSAT events explicitly request `visibility: 'private'`; a missing/public visibility receipt is uncertain and cannot be accepted. A trusted summary construction failure returns 503 before Calendar; it never degrades into a generic booking without the validated answers. Private event evidence is persisted before insert and required again in reconciliation. This leaves generic/SAT/consulting visibility behavior unchanged. Calendar privacy still permits the attendee and calendar writers to see the event; owner sharing/identity remains a live gate, not a claim of complete access isolation. Google reference: https://developers.google.com/workspace/calendar/api/v3/reference/events

The exact event resource is persisted before insert. A provider success is acknowledged only after the durable outcome is recorded. Timeout, worker crash, provider failure or persistence failure leaves a pending/unknown reservation; HTTP retries never insert a second event. Internal `reconcileByQuizId(quizId, lookup)` reads the existing event using the same ID and accepts only exact submitted summary/contact/answer/private fields and equivalent start/end instants. Google-added timezone offsets are handled. Missing/cancelled/mismatching evidence remains blocked. It never inserts, emails, uses a new ID or treats absence as permission to resend. A crash before event persistence needs authenticated operator recovery; no blind automatic retry is supplied.

SHSAT bookings use the Calendar invitation as confirmation. They do not independently send the legacy Resend confirmation or strategy-call tracker. Generic/SAT/consulting paths retain their existing behavior. The existing platform booking/no-show relay is preserved through the new durable delivery contract below. Thank-you routing and conversion labels remain unchanged; no answers/contact details are placed in public URLs, general logs or ad tags.

## Existing post-booking operations relay

After confirmed private Calendar acceptance, the same database transaction records acceptance and an encrypted immutable relay payload in the existing booking row. There is no gap in which Calendar is accepted but a pending relay is forgotten. Payload fields are exactly `source`, `type`, `name`, `email`, `phone`, `start`, `end`, `google_event_id`, `meet_link`. Values come from the persisted intake/event, not another browser submission. No quiz answers/ID/description/band, click IDs, attribution, referral code or arbitrary URLs are relayed. Only a query-free HTTPS Google Meet link is retained. Existing ops source reads the phone/Meet link and consultation_bookings record for booking/no-show alerts.

`createSiteBookingSender` posts only to the existing `https://app.ivypathacademy.com/api/bookings/site`, using the existing `SITE_BOOKING_RELAY_SECRET`. Redirects are forbidden and the request is aborted after two seconds. A successful status alone is insufficient: the receiver must acknowledge `ok:true` with its booking-row UUID. The deterministic Calendar ID is the receiver's existing deduplication key and is also sent as Idempotency-Key. Receiver source/migration00105 declares that ID unique; live presence must be independently verified. The receiver continues to own ops records/alerts; this code sends no direct Discord message or pre-booking mail.

The database leases one due delivery across instances for 60 seconds, fences acknowledgements with a unique claim ID, and retries the identical payload/key after unknown receiver outcomes. Backoff starts at 5 seconds, doubles to a one-hour cap, and stops at 12 claims as `blocked` for owner recovery. A crash after receiver commit but before local acknowledgement can produce another HTTP request; receiver deduplication must produce the same platform record and preserve downstream deduplication. This is at-least-once delivery, not a claim of exactly one HTTP call. A delivered job never sends again. Stale workers cannot acknowledge a new lease. Pending records survive intake expiry and process restarts. One failed job does not starve unrelated batch items.

Initial booking acceptance and exact accepted HTTP replay both attempt a due relay without changing the bound Calendar response or re-inserting Calendar. Authenticated `createBookingRecovery` reconciles only exact private existing Calendar evidence, atomically prepares the job and attempts delivery; it also retries a due job for an already accepted event. `retryPending(limit)` is an internal server function, bounded to 1–20 jobs. It has no public HTTP endpoint. An existing approved recovery runner must call it and monitor pending/blocked states; no new cron, service, credentials, schedule or persistent access is provisioned here. Without that runner binding, production durability is incomplete even though requests/replays can deliver.

## Owner-ready SQL and server wiring

`db/shsat-booking-owner-review.sql` creates the three isolated ledger tables. `db/shsat-relay-owner-review.sql` adds relay state/payload/claim/lease/attempt columns, constraints and a due-work index to the booking table, with no new table/service. Fresh installs apply those two reviewed SQL drafts in order, then `db/shsat-booking-grants.psql` for an already approved dedicated existing role. If an f00c722 ledger/role is already installed, apply the reviewed relay SQL and `db/shsat-relay-grants.psql` for only the additional column UPDATE grants; do not rerun the non-idempotent initial policies. Existing accepted records without private Calendar evidence are not silently backfilled. All SQL/grant changes here are drafts and were applied ONLY to disposable local Postgres 17 under a NOLOGIN/NOBYPASSRLS fixture role. No production query/application occurred.

`createShsatRuntime({env,book,lookup})` is an unbound constructor in `api/_shsat-runtime.js`. It validates configuration before constructing a lazy bounded pool and returns `bookingHandler`, authenticated-server `reconcile`, internal `retryPending` and `close`. `book` is the existing Calendar handler; `lookup` must be the authenticated read-only Google events.get adapter for the same verified business calendar. No connection/provider request or credential lookup occurs at import. The public immutable policy remains `{captureHandler:null,bookingHandler:null}`; constructor availability or an environment variable does not activate it.
